# CoCo CLI Session Log — Harbour Street Cafe AI Copilot

This document is a cleaned-up, narrated transcript of the actual CoCo CLI
session used to build the Snowflake backend for this project: schema
creation, semantic view design, Cortex Agent setup, bug discovery/fixes,
and row-level access control. Nothing here is staged — every SQL query,
error, and fix shown below happened in the real session and was verified
against the source data.

---

## 1. Schema, Semantic View & Ingredient-Level Joins

**What this stage verified:** that CoCo could build a semantic view on top
of a normalized, multi-table schema (7 tables spanning two businesses) and
correctly connect purchase, sales, and vendor data through a shared
`INGREDIENTS` hub table.

Initial relationships CoCo generated only connected each table back to
`BUSINESSES`. The ingredient-level tables (`PURCHASE_DETAIL`,
`INGREDIENT_SALES_LINK`, `VENDOR_PRICE_COMPARISON`) were islands — none of
them could be joined to each other, which meant the core "purchase vs.
sales" scenario was impossible to answer.

**Fix requested:** add `INGREDIENTS` as a table in the semantic view and
link all three ingredient-related tables to it via `INGREDIENT_ID`.

**Result — 6 relationships confirmed:**

| Relationship | From | To | Join Key |
|---|---|---|---|
| SALES_TO_BUSINESSES | SALES_DETAIL | BUSINESSES | BUSINESS_ID |
| INGREDIENT_SALES_TO_BUSINESSES | INGREDIENT_SALES_LINK | BUSINESSES | BUSINESS_ID |
| PURCHASE_TO_BUSINESSES | PURCHASE_DETAIL | BUSINESSES | BUSINESS_ID |
| PURCHASE_TO_INGREDIENTS | PURCHASE_DETAIL | INGREDIENTS | INGREDIENT_ID |
| INGREDIENT_SALES_TO_INGREDIENTS | INGREDIENT_SALES_LINK | INGREDIENTS | INGREDIENT_ID |
| VENDOR_PRICE_TO_INGREDIENTS | VENDOR_PRICE_COMPARISON | INGREDIENTS | INGREDIENT_ID |

## 2. First End-to-End Test: Salmon Purchase vs. Sales Correlation

**What this stage verified:** that the newly-connected schema could
actually answer the flagship business question — comparing purchase
volume of an ingredient against the sales of every menu item tagged with
that ingredient, without any precise gram-level recipe data (tagging only).

**Question asked:**
> "Compare the trend of salmon purchase volume against the trend of
> salmon-related menu item sales."

**SQL generated by the agent:**
```sql
WITH __purchase_detail AS (
  SELECT ingredient_name, week_start, pack_size AS purchase_pack_size, qty_packs
  FROM SNOWFLAKE_LEARNING_DB.ANALYTIC.PURCHASE_DETAIL
),
__ingredient_sales_link AS (
  SELECT ingredient_name, sale_date AS ingredient_sale_date, total_qty_sold
  FROM SNOWFLAKE_LEARNING_DB.ANALYTIC.INGREDIENT_SALES_LINK
),
salmon_purchases AS (
  SELECT DATE_TRUNC('month', week_start) AS month,
         SUM(qty_packs * purchase_pack_size) AS purchase_volume
  FROM __purchase_detail
  WHERE LOWER(ingredient_name) LIKE '%salmon%'
  GROUP BY DATE_TRUNC('month', week_start)
),
salmon_sales AS (
  SELECT DATE_TRUNC('month', ingredient_sale_date) AS month,
         SUM(total_qty_sold) AS sales_volume
  FROM __ingredient_sales_link
  WHERE LOWER(ingredient_name) LIKE '%salmon%'
  GROUP BY DATE_TRUNC('month', ingredient_sale_date)
)
SELECT COALESCE(p.month, s.month) AS month,
       COALESCE(p.purchase_volume, 0) AS purchase_volume,
       COALESCE(s.sales_volume, 0) AS sales_volume
FROM salmon_purchases p
FULL OUTER JOIN salmon_sales s ON p.month = s.month
ORDER BY month DESC NULLS LAST
```

**Result:**

| Month | Salmon Purchased (kg) | Salmon Menu Items Sold |
|---|---|---|
| July 2026 | 209 kg | 1,331 items |
| August 2026 | 0 kg | 114 items |

✅ Verified against source CSVs — exact match, including the correct
observation that August had zero new purchases but non-zero sales
(inventory carryover from July).

## 4. Bug Found: Unbounded Date Filters

**What this stage verified:** whether "this month" / "this week" questions
were being scoped correctly — this is where a real bug was caught and fixed.

**Original query for "salmon items sold this month":**
```sql
WHERE item_name ILIKE '%salmon%'
  AND sale_date >= DATE_TRUNC('MONTH', CURRENT_DATE)
```
Answer returned: **1,445 items**.

**Problem:** no upper bound. Since the mock dataset extends a few days into
August, the query silently included August 1–2 data inside a "this month
(July)" answer.

**Fix requested and applied:**
```sql
WHERE item_name ILIKE '%salmon%'
  AND sale_date >= DATE_TRUNC('MONTH', CURRENT_DATE)
  AND sale_date <  DATE_TRUNC('MONTH', CURRENT_DATE) + INTERVAL '1 MONTH'
```
Corrected answer: **1,331 items** — verified exactly against source data
(1,331 for July only, vs. 1,445 for July+August combined).

The same unbounded-lower-bound issue was then found and fixed for **"this
week"** queries:

| Query | Before fix | After fix | Verified |
|---|---|---|---|
| Discount loss "this week" | NZD $1,537.98 | NZD $770.32 | ✅ matches source (Jul 20–26 only) |
| Nishi Asian Foods spend "this month" | NZD $70,838.70 | NZD $70,838.70 (unchanged — all purchases happened to fall in July) | ✅ |

The agent's instructions were updated so both "this month" and "this week"
questions always apply a bounded date range going forward — this was a
one-time fix that self-propagates to all future time-scoped questions, not
a one-off patch.

## 5. Row-Level Security: Multi-Tenant Isolation

**What this stage verified:** that one business's Role cannot see another
business's data, at the Cortex Agent level — the core governance story of
the project.

**First attempt — native Row Access Policy:**
```sql
CREATE ROW ACCESS POLICY BUSINESS_ACCESS_POLICY ...
```
❌ Failed: `Unsupported feature 'ROW ACCESS POLICY'` — this trial account is
on Standard Edition; Row Access Policies require Enterprise Edition or
higher.

**Workaround chosen:** secure views filtering on `CURRENT_ROLE()` via a
`BUSINESS_ROLE_MAP` mapping table, applied directly to the same views the
semantic view already depends on (`SALES_DETAIL`, `PURCHASE_DETAIL`,
`INGREDIENT_SALES_LINK`, `BUSINESSES`) — so the semantic view and Cortex
Agent required zero changes to inherit the filtering.

```sql
-- BUSINESS_ROLE_MAP
('HSC_OWNER_ROLE', 'HSC001')
('NON_OWNER_ROLE', 'NON002')
```

Each secure view includes:
```sql
WHERE business_id IN (
  SELECT business_id FROM RAW.BUSINESS_ROLE_MAP
  WHERE role_name = CURRENT_ROLE()
)
```

**Verification with actual role switches (not simulated):**
```sql
USE ROLE HSC_OWNER_ROLE;
SELECT business_id, COUNT(*) FROM ANALYTIC.SALES_DETAIL GROUP BY business_id;
-- HSC001 | 784

USE ROLE NON_OWNER_ROLE;
SELECT business_id, COUNT(*) FROM ANALYTIC.SALES_DETAIL GROUP BY business_id;
-- NON002 | 420
```
✅ 784 + 420 = 1,204 = total row count of `daily_sales_all.csv`. Confirmed correct.

## 6. Final Test: Agent-Level Isolation Between Businesses

**What this stage verified:** the end-to-end governance story — the same
natural-language question, asked under two different roles, returns
completely different (and correctly isolated) answers.

**Question asked under both roles:**
> "Which business had higher revenue this month, Harbour Street Cafe or
> Nonna's Trattoria?"

**As `HSC_OWNER_ROLE`:**
> "Harbour Street Cafe had higher revenue this month with NZD 87,386.79.
> Note: Nonna's Trattoria has no sales data available in the system for
> July 2026 (or any other period)."

**As `NON_OWNER_ROLE`:**
> "Nonna's Trattoria had higher revenue this month with NZD 57,456.91.
> However, I should note that the sales data currently only contains
> records for Nonna's Trattoria... There are no sales records for Harbour
> Street Cafe in the database at this time."

✅ Both revenue figures verified exactly against source data
($87,386.79 and $57,456.91).

**Why this matters:** the agent didn't just filter numbers — from its own
point of view, the other business's data doesn't exist. This demonstrates
that access control is enforced at the SQL execution layer, beneath the
AI, not by the AI "being told" to withhold information. A prompt cannot
talk its way around a role that was never granted access.

## Summary of Issues Found & Fixed During This Session

| # | Issue | Root Cause | Fix |
|---|---|---|---|
| 1 | Ingredient-level tables couldn't be joined | No shared hub table in semantic view relationships | Added `INGREDIENTS` as central table, linked 3 tables to it |
| 2 | "This month" totals inflated by ~8% | Date filter had no upper bound | Enforced `>=` and `<` bounds, applied as a standing agent instruction |
| 3 | "This week" totals inflated by ~2x | Same unbounded-filter issue, week granularity | Same fix, applied to week-level queries |
| 4 | Row Access Policy unavailable | Standard Edition account doesn't support native RAP | Implemented equivalent filtering via secure views + role-mapping table |

Every number in this document was independently verified against the
underlying mock CSV datasets before being accepted as correct.
